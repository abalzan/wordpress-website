**Verdict: it could directly cause production mutation.** A capability and a
nonce were the entire authorisation story.

## DECISIVE REPOSITORY EVIDENCE FOR THE DISPOSITION

Which plugins register a stage with the engine (shipped code, excluding tests):

  conexao-en-translation  -> production: false, build: false, status: active
  conexao-job-translation -> production: false, build: false, status: retired

The production steady state is exactly:
  conexao-data-model -> conexao-content -> conexao-admin-ux ->
  conexao-event-runtime -> conexao-translation-rollout -> conexao-translation-automation

NO production plugin registers a stage. So in production
`Engine::get_stage()` returned null for every input and `handle_run()` could
only ever have reached its `unknown stage` 400. **The bypass was latent, not
load-bearing** - which is exactly why it had to be closed rather than left
merely declared.

## THE CLOSURE

handle_run() is now: capability check, then wp_die(410) naming the
replacement. The file contains NO call_user_func, NO run_callback, NO Engine::
reference and reads NO superglobal, so no request value can become a mode.
