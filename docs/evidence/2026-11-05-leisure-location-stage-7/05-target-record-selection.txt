## 4. Original values — exact representation

| Key | Value as production REST exposes it | Note |
|---|---|---|
| `_leisure_lat` | `""` (empty string) | **Not** `null` and **not** absent from the `meta` object. |
| `_leisure_lng` | `""` (empty string) | same |

Why this matters, precisely: WordPress core's `WP_REST_Meta_Fields::get_value()`
returns `$args['schema']['default']` when a single meta key has **no rows** — which
for `type: string` is `""`. So an empty string over REST means *"no coordinate"*,
but it does **not** prove whether a `postmeta` row exists. That distinction is
unobservable without database access, which production does not offer
(WordPress.com: no SSH/WP-CLI/DB). See `07-authorization-checkpoint.txt` for how
the restore handles it.

## 6. Side effects that cannot be reverted over REST (disclosed before authorisation)

A REST post update is not a meta-only operation: `WP_REST_Posts_Controller` calls
`wp_update_post()`, so **every** update on this post type also:

1. moves `post_modified` / `post_modified_gmt` (permanent; `modified` is read-only
   in the REST schema);
2. creates a **revision** (`leisure` declares `revisions` support) — permanent,
   because revisions are not deletable over REST;
3. flushes the theme's language-scoped homepage/404 transients (self-healing).

Nothing else in the record changes: title, slug, status, content, dates, taxonomies,
Polylang relations and every other meta key are not sent, and no `save_post` handler
for this post type writes them from a REST request (the data-model and admin-UX meta
writers both return early without their admin nonces — `class-meta.php::save_meta()`
and `conexao-admin-ux/includes/class-editor.php::save()`).
