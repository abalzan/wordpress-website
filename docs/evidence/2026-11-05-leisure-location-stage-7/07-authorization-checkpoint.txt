**Why these test values:** both are inside the sanitizer's valid ranges
(lat −90..90, lng −180..180) and canonicalise unchanged, so a `200` is a genuine
accepted write rather than a value coerced to `""`. They are deliberately synthetic
and far outside Ireland, so (a) they cannot be mistaken for real content if a
restore ever failed, and (b) the record sorts *last* — not first — in the proximity
ordering for real visitors during the seconds the value exists.

## 2. Original values and why the restore is exact

| Key | Original (production REST) |
|---|---|
| `_leisure_lat` | `""` |
| `_leisure_lng` | `""` |

The restore writes back exactly the value the original state exposes over REST.
Two residuals are possible and are disclosed rather than hidden:

1. If no `postmeta` row exists today, the restore leaves a row holding `""`. To
   every consumer this is identical to absence: `get_coordinates()` returns `null`
   for `""`, `coordinate_status()` reports `missing`, and the public dataset returns
   `lat: null`. Row-level absence is **not observable** from outside (no DB access
   on WordPress.com), so it can be neither proven nor removed over REST.
2. `post_modified` / `post_modified_gmt` move and one **revision** is created. Both
   are consequences of `wp_update_post()` inside the REST controller, outside the
   two meta keys, and neither is revertible over REST (`modified` is read-only;
   revisions are not deletable). They are measured before/after and reported.

Failure handling is built in and closed:

| Failure | Behaviour |
|---|---|
| Step 2 returns 403 `rest_cannot_update` | **abort**: nothing was written; re-read proves the record is unchanged; exit 2 (this is also the signal that the deployed plugin is *not* 1.6.3) |
| Step 2 succeeds but step 3 disagrees | the restore at step 4 still runs; exit 1 |
| Step 4 fails | **INCIDENT**: exit 3, sanitized state printed, no retry, no migration |
| Any 429 | retried with `Retry-After`, bounded |
