Stage 2 verification — engine-enforced read-only transaction probe
=================================================================
Captured 2026-11-15, before any data query in this task.
Database server: MySQL 9.7.1 (MySQL Community Server - GPL), host db, port 3306.
Account: root@localhost (MySQL administrative account from the local compose
configuration). The WordPress application account (wordpress) was NOT used.

--- Session facts before the probe -------------------------------------------
$ mysql -uroot --batch --raw -e "SELECT VERSION() AS version,
    @@transaction_read_only AS txn_ro_default, @@autocommit AS autocommit,
    @@version_comment AS vcomment, CURRENT_USER() AS who;"
version	9.7.1
txn_ro_default	0
autocommit	1
vcomment	MySQL Community Server - GPL
who	root@localhost

--- PROBE (exact statement sequence, probe.sql) ------------------------------
SET SESSION TRANSACTION READ ONLY;
START TRANSACTION READ ONLY;
SELECT @@transaction_read_only AS session_txn_ro_inside_txn;
UPDATE wordpress.wp_posts SET post_title = post_title WHERE 1 = 0;
SELECT 'PROBE_UNEXPECTEDLY_REACHED_AFTER_UPDATE' AS marker;
ROLLBACK;

--- PROBE OUTPUT (exit status 1) ---------------------------------------------
session_txn_ro_inside_txn
1
ERROR 1792 (25006) at line 4: Cannot execute statement in a READ ONLY transaction.

The marker SELECT after the UPDATE never printed: the client aborted the script
at the ERROR, the session closed without COMMIT, and no transaction state
remained. ROLLBACK was therefore not reached (closing the connection ends the
session and rolls back).

--- ASSERTION -----------------------------------------------------------------
SQLSTATE 25006 / error 1792 is MySQL's READ-ONLY-transaction rejection, not an
access-denied error (1142). The rejection is produced by the storage engine's
transaction state, so it holds for every statement class that writes, not only
for UPDATE, and it holds for the administrative account. Engine-enforced
read-only is therefore VERIFIED for this account and server.

The probe proves enforcement, not merely convention:
  * `SET SESSION TRANSACTION READ ONLY` alone already makes later statements
    read-only, and `START TRANSACTION READ ONLY` states it explicitly;
  * `@@transaction_read_only` reported 1 inside the transaction;
  * the guard fired on a statement whose WHERE clause matches no row, so the
    rejection happens at statement validation, before any row is touched.

--- POST-CAPTURE RE-PROBE -----------------------------------------------------
The identical probe was re-run after every data capture completed, to confirm
the engine still enforced read-only at the time of the captures. Same result:
  ERROR 1792 (25006) at line 4: Cannot execute statement in a READ ONLY transaction.
See 01c-cohort-fingerprints.txt §9 for the post-check state comparison.

--- WHY THE STAGE 2 REPORT WAS WRONG ------------------------------------------
The Stage 2 report (and `docs/evidence/2026-11-15-stage-2/00-baseline-and-scope.md`
§4) reasoned that the read-only transaction path was "only reachable through an
existing account" and that the only accounts were the application account
(forbidden) and root. It treated root as unusable because "creating/altering
accounts or privileges is forbidden". That conflates two different things:

  * using an existing administrative account to open a read-only transaction
    (what this task did — no account or privilege was created, altered, or
    granted), and
  * creating a new read-only account (what Stage 2 correctly avoided).

The first was always available and needs no access-control change. The
limitation recorded by Stage 2 was therefore a limitation of the attempt, not of
the environment.
