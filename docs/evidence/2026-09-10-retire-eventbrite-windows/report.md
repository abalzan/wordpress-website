## 1. What was asked

Remove all events from the event-import plugin that contain `(This week)`,
`(Today)` and `(Tomorrow)`.

## 2. What those strings are

They are the 78 Eventbrite **date-window source registrations** added by the G8
expansion — `eventbrite_<county>_events_{today,tomorrow,this_week}`
(26 counties × 3 windows), shown in Event Import → Event Sources as
`Eventbrite — <County> (Today)`, `Eventbrite — <County> (Tomorrow)` and
`Eventbrite — <County> (This week)`. They are the only objects in the plugin
whose text contains those three parenthesised markers:

- **0** event post titles contain them (measured, `01-inventory-before.txt`);
- **0** imported events carry a window `_event_source` (measured, `01-inventory-before.txt`);
- the registry *generates* 78 of them per read (`01-inventory-before.txt`).

So this change is a **registry change, not a content deletion**: no event post,
term, image or translation was created, updated or deleted at any point.

## 6. The two pre-existing failures (proved unrelated)

Both fail identically at the base SHA `3b8532e` with this change stashed:

1. `test-ics-occurrence-dates.php` (1 fail): `next_occurrence_date()` is keyed on
   *today*; the test hardcodes `2026-10-06`, which is only correct while today
   falls in 2026-09-30 … 2026-10-05. A time-bomb expectation, nothing to do with
   Eventbrite sources. Baseline proof: `09-baseline-ics-failure.txt` (171 passed, 1 failed).
2. `test-town-sanitization.php` (1 fail): the local database already holds
   Eircode-contaminated `conexao_town` terms; a DB-state expectation, nothing to
   do with Eventbrite sources. Baseline proof: `10-baseline-town-failure.txt`.
3. The single HTTP acceptance failure (`verify-event-occurrence-http.py`, Laois
   archive occurrence assertions) is the same date/DB-state family.

fully green; the two in-process failures and the acceptance failure exist at

  definition of the retired shape; both the strip logic and the tests reference
  it.
