# 06 - Phase 11: HTTP acceptance - route matrix, and the REWRITE-RULE finding

Base: http://localhost:8080 (local Docker). Redirects NOT followed.

## THE CRITICAL FINDING: stale rewrite_rules in the local DB

Restoring the source was necessary but NOT sufficient. The stored rewrite_rules
option had been generated while the destructive functions.php was active, so the EN
CPT-archive rules that the restored theme registers were ABSENT from the database:

  before flush: 84 rules carrying an en/ prefix, of which 0 for a CPT archive
  after  flush: 92 rules carrying an en/ prefix for a CPT archive   (0 -> 92)

The rules existed ONLY for the PT roots (guias/?$ => index.php?post_type=guide,
eventos/?$ => index.php?post_type=event, lazer/?$ => index.php?post_type=leisure)
with no en/ counterpart. That is exactly why /en/guias/ and /en/eventos/ returned
404 and /en/lazer/ redirected to PT even after a byte-perfect source restore.

A local flush_rewrite_rules(true) - the documented operation also performed by
scripts/flush-navigation-rules.php - regenerated them. This is a LOCAL DATABASE
operation only: no production write, no code change, no file committed.

## /en/empregos/ - why it still 302s (documented policy, NOT a regression)

Measured:
  page "empregos" ID=11293 lang=pt   (no EN translation exists)
  conexao_b2_page_allowlist() = dublin, cork, galway, limerick, kildare, meath,
                                wicklow, waterford, laois, irlanda, blog
                                (empregos is NOT listed)

The restored code therefore applies the documented B1 policy, which is the CORRECT
behaviour, quoting the restored source itself:
  inc/i18n/fallback.php:271  "B1 = Guides, Blog posts, key narrative static pages:
                                keep the approved 302 policy until a real
                                translation exists (never render fallback)."
  inc/i18n/fallback.php:304  "B2 is never a catch-all and never a substitute for
                                editorial translation."
  docs/routing.md:94         "stays B1 (302 -> PT) or serves a real translation."

The same content gap is reported independently by the translation_completeness
permanent gate: "page: eligible public PT records missing a linked EN translation
= 0" -> 4 violations (empregos, contato, sobre-nos, inicio).

Making this route return 200 would require CREATING EN page translations, i.e. a
content change: forbidden by constraint 3 (no content mutation) and out of scope
for a code recovery. It is a pre-existing content gap, identical at b47d098, and
is NOT a code regression. The B2 fallback architecture itself is restored and
demonstrably working (B2-eligible types: event, leisure, sponsor, course_provider,
job; and /en/eventos/ + /en/lazer/ + /en/cursos/ now serve lang=en-US).
