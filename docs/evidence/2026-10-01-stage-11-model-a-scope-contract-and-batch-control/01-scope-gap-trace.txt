    THE NARROWED MANIFEST IS BUILT, VALIDATED, DIGESTED — AND THEN DROPPED

This is precisely Stage 10's reported gap, now confirmed at line-level.

--- 6. Can an explicit subset be introduced without duplicating lifecycle? --

YES. Every downstream lifecycle function iterates $manifest['records']:
    collect_states()      line 508  foreach ( $manifest['records'] ... )
    build_plan()          line 236  foreach ( $manifest['records'] ... )
    capture_snapshots()   line 551  foreach ( $manifest['records'] ... )
    apply_plan()          line 579  foreach ( $plan['create']/$plan['update'] )
    assert_no_pt_drift()  line 771  foreach ( $snapshots ... )
    collect_verify()      line 403  foreach ( $manifest['records'] ... )

So ONE narrowing of $manifest['records'], applied AFTER validate_manifest()
and BEFORE collect_states(), propagates through the ENTIRE lifecycle:
inventory, plan, snapshot, apply, PT-drift, verify and the numeric gate.

--- 7. Can every stage's run_callback carry the scope unchanged? -------------

YES — this is the decisive fact. All four run_callbacks forward $args
verbatim into Engine::run( ..., $args ):
    stage-config.php:199-203     $run_args
    leisure-description-stage:403-407   $args
    course-provider-description:392-396 $args
    job-translation:193                  $args

So a 'scope' key inside $args reaches Engine::run() with ZERO stage changes.

--- 8. Whether filtering before planning preserves all safety gates ---------

YES, because filtering happens before, and every gate then evaluates over
exactly the scoped records:
  - validate_manifest() still runs over the FULL authored manifest, so a
    malformed or duplicated authored row still fails closed;
  - build_plan() classifies skip/conflict for every SCOPED row, so an
    approved-but-impossible row becomes a conflict and FAILS the gate
    rather than being silently dropped;
  - assert_no_pt_drift() still diffs before/after for every scoped PT record;
  - collect_verify()/calculate_gate() still count eligible/with_en/conflicts/
    pt_drift over the scoped records;
  - apply_plan() only ever sees plan categories derived from the scoped rows.
No gate is bypassed; every one is evaluated over the approved subset.

CONCLUSION: Model A is feasible with ONE new validated argument on the
EXISTING engine, and no change to any stage, adapter or lifecycle function.
