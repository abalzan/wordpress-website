=== The credential boundary, proven at runtime ===

1. No credential in the environment -> FAILS CLOSED, no request made:
   error code : conexao_automation_provider_no_credential
   HTTP calls : 0  (must be 0)

2. A credential-shaped FAKE key appears in NO observable output
   (asserted over 7 provider outcomes + configuration + identity + token):
   PASS: no observable provider output contains the credential or an authorization header
   PASS: the credential is sent as a bearer header, which is the vendor contract
   PASS: the credential never appears in the request body

3. No provider credential literal in the automation plugin source:
   $ grep -rIn 'sk-' wp-content/plugins/conexao-translation-automation/
   tests/test-automation-translation-plan.php:658:  false === strpos( $body, 'sk-' ),

   The single hit is the TEST THAT ASSERTS ITS ABSENCE — the scan pattern
   inside an assertion, not a credential. There is no credential literal in the
   plugin.

   NOTE on method: a repository-wide `grep -rIn 'sk-'` DOES return hits, but
   every one is a false positive in pre-existing unrelated data, e.g. the
   Eventbrite URL "dusk-2-dawn-tickets-..." in
   conexao-event-importer/tests/c2-baseline-post-remediation.json and CSS
   "mask-image"/"--si-fill-mask" in conexao-event-importer/tests/fixtures/
   mi-listing.html. None is in the translation-automation plugin, and none was
   introduced by Stage 4. The check is therefore scoped to the plugin that owns
   the credential.

4. The credential VARIABLE NAME appears in exactly ONE plugin source file —
   the configuration boundary, where it is NAMED and never given a value:
   wp-content/plugins/conexao-translation-automation/includes/class-conexao-translation-automation-provider-config.php

   (It is also named, correctly, in this stage's own report, evidence and
   structural gate — documentation and tests may name the variable; no
   credential VALUE exists in any of them. The Stage 4 gate asserts this.)
