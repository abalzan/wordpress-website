## 1a. Independent re-verification and proven root cause

The preflight was re-run independently on the same HEAD (`464a353`) and the same local stack, reading the raw `conexao_event_sources` option directly. `Conexao_Event_Sources::get_all()` was deliberately **not** used, because it self-heals and can persist a write. Result: **154 records, all `active`; exactly 18 anchored `^g1_probe_*`; both named IDs absent.** Identical gate outcome — `BLOCKED`, 18 of 20, zero writes. Evidence: `preflight-recheck.json`.

**Why the two named IDs cannot be deactivated.** They are not configurations at all. They are runtime fixtures created inside test code:

| ID | Created by |
|---|---|
| `g2_cavan_probe` | `tests/test-source-pagination-completeness.php:470-485` — `$plugin->sources->save([...])` |
| `g4c_budget_probe` | `tests/test-request-budget.php:276-289` — `$plugin->sources->save([...])` |

Run All scope comes from `$this->sources->get_active()` (`class-event-importer.php:195`), which iterates the registry via `get_all()` (`class-event-sources.php:256`). A source with no registry record can never be selected, so neither ID is "treated as an import target", and neither has a `status` field for Stage 0 to change. The authorised 18 + 2 manifest is therefore **unsatisfiable by construction**, not merely mismatched on this dataset.

What the fixtures did leave behind is event residue, not configuration: post `103699` (`g2_cavan_probe`, source id `9300000001`, "G2 partial listing event") and post `103692` (`g4c_budget_probe`, source id `9400000001`, "G4C page-one event"), both `publish` and `_event_status=published`, created 2026-10-09. Source health also retains a `g2_cavan_probe` record. None of this was touched.

**The 18 G1 records are genuine live import targets.** Their IDs are generated by `tests/test-source-fetch-failure.php:156` (`'g1_probe_' . $type . '_' . substr( md5( $type . $url . microtime( true ) ), 0, 8 )`). All 18 carry a source-health record and all 18 were imported by the audited Run All between 17:06 and 17:25, every one recording `last_import_status = error` with `HTTP status: 429`. The current revision of that test isolates `Conexao_Event_Sources::OPTION_KEY` and deletes every `g1_probe_*` record before finishing, so this is residue from an interrupted or pre-isolation pass — not current test behaviour.

**New finding — duplicate-feed amplification.** The 10 Eventbrite probes point at `https://www.eventbrite.ie/d/ireland--laois/all-events/`, the same URL as `eventbrite_laois` and the bare `eventbrite` source. **Twelve active sources enumerate one identical discovery feed on every Run All.** The 8 Heritage Week probes similarly duplicate `https://www.heritageweek.ie/event-listings`. This multiplies the P1 request storm and the P7 over-fetch independently of the four date-window variants.

The 14 probe-associated events the audit requires to remain untouched are confirmed: 12 under G1 probes, 1 under `g2_cavan_probe`, 1 under `g4c_budget_probe`.
