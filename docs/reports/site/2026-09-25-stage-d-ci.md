## 2. CI workflow

**Path:** `.github/workflows/ci.yml` — the single canonical CI entrypoint
(name: `WordPress CI`). No other workflow file exists.

| Aspect | Implementation |
|---|---|
| Triggers | `push` (**every branch**, no path filters), `pull_request`, `workflow_dispatch` |
| PR safety | `pull_request` (never `pull_request_target`); untrusted PR code gets no secrets and no write scopes |
| Push safety | every branch, including feature branches — regressions are caught before merge |
| Permissions | `contents: read` only. No `issues:`, `pull-requests:`, `actions:`, `deployments:` or `contents: write` |
| Runner | `ubuntu-latest`, `timeout-minutes: 30` |
| Checkout | `actions/checkout@v4` (no SSH keys, no repository secrets) |
| PHP setup | `shivammathur/setup-php@v2`, `php-version: '8.5'`, `tools: composer:v2` |
| Composer setup | `composer validate --strict` → `composer install --no-interaction --prefer-dist --no-progress` → explicit lockfile-unchanged assertion |
| Cache | `actions/cache@v4` on `~/.cache/composer`, key `composer-downloads-${{ runner.os }}-${{ hashFiles('composer.lock') }}` (+ `restore-keys` fallback). Downloads only — never `vendor/`, WordPress runtime state, credentials or data; the install always runs from the lockfile, so a cache hit cannot replace it |
| Concurrency | `group: ${{ github.workflow }}-${{ github.ref }}`, `cancel-in-progress: true` — obsolete runs of the same ref are cancelled; unrelated branches/PRs are never grouped together and the latest commit always receives a result |
| Secrets | **none** — no `secrets.*`, no placeholder credential names |
| Structure | one job (`static-quality`) with ordered steps; no Docker/WordPress boot, no browser/REST/visual/deploy/migration job |

**PHP version policy (unchanged).** CI runs PHP **8.5** because that is the
toolchain version Stage C verified (8.5.8). This does **not** change the
declared compatibility floor, which stays **8.0** (`phpcs.xml.dist`
`testVersion: 8.0-`; standard §2.1). No `Requires PHP:` header was touched.
The locked toolchain's own constraints (`phpstan ^7.2`, `wpcs ^7.4||^8.0`, …)
are compatible with 8.0 and above, so there is no floor-vs-lockfile
incompatibility to report.

**A real defect was caught during authoring.** The first draft used
`tools-cache: true` on `setup-php`; **actionlint rejected it**
(`input "tools-cache" is not defined in action "shivammathur/setup-php@v2"`).
It was replaced with an explicit `actions/cache@v4` step. This is the
concrete reason the workflow was linted rather than eyeballed.

## 3. Blocking gates

Every command below is blocking: a non-zero exit fails the job. There is no
`continue-on-error` and no `|| true` on any of them.

| Command | Role |
|---|---|
| `composer validate --strict --no-interaction` | `composer.json` is well-formed **and `composer.lock` is in sync with it** — the lockfile-consistency failure mode. |
| `composer install --no-interaction --prefer-dist --no-progress` | Deterministic install **from the committed lockfile**. CI never runs `composer update`; dependencies are never re-resolved. |
| *(lockfile assertion)* | `git diff --quiet -- composer.json composer.lock` after the install — proves CI itself cannot mutate the lockfile. |
| `./scripts/lint.sh` | **The primary quality gate** (the Stage C regression gate, semantics untouched): `[1/3]` PHP syntax sweep `php -l` over every Git-known PHP file · `[2/3]` PHPCS vs `phpcs-baseline.json` (legacy debt recorded, NEW violations fail) · `[3/3]` PHPStan level 5 via `composer analyse` (baseline isolates legacy errors, NEW errors fail). |
| `shellcheck scripts/*.sh` | Repository shell scripts. ShellCheck is installed **explicitly** from apt in the workflow — the runner image ships a copy, but its presence is not a documented guarantee, so the gate does not rely on it. |

`./scripts/lint.sh` is invoked directly; its implementation is **not**
duplicated, and no second PHP-file-discovery algorithm exists in CI. The
telemetry step (§4) is the only `continue-on-error: true` in the file.

## 4. Legacy PHPCS semantics

**Raw legacy debt remains and is not paid down by this stage.**

- Measured legacy debt, re-confirmed during Stage D: **3290 errors + 2672
  warnings** in 156 files, **129 sniff classes** (`phpcs-baseline.json`
  totals: errors 3290, warnings 2672, fixable 4901, files 156). This matches
  the baseline **exactly** — zero growth.
- `./scripts/lint.sh` is the **no-new-violations** gate and is the blocking
  lint command. `composer lint` is **not** the sole blocking lint command.
- `composer lint` runs only as a clearly-labelled **non-blocking telemetry**
  step (`if: always()`, `continue-on-error: true`, header "Telemetry
  (non-blocking) — raw legacy PHPCS debt"). Its known non-zero exit
  **cannot** fail an otherwise-valid run: the step is marked
  continue-on-error *and* the command is `composer lint || echo
  "::warning::…"`. Full output is preserved; nothing is suppressed, no
  baseline is updated, no commit is generated, no source file is mutated.
- **CI does not require legacy debt to be zero.** The objective is
  *debt must not grow*.
- The `phpcs-baseline.json` file was **not** regenerated or edited by Stage D.

`composer check` is not in the workflow at all: it is `@lint` + `@analyse`
and is red for the same by-design reason as `composer lint`; adding it as a
gate would make CI permanently red, which this stage explicitly must not do.

## 11. Known limitations

Real limitations observed during Stage D:

1. **A real GitHub Actions run was not observed** (§8). The workflow is
   implemented, actionlint-clean and reproduced locally, but the
   GitHub-hosted execution could not be triggered from this environment (no
   push credentials). This is the sole reason for the `PASS WITH LIMITATION`
   status. Outstanding action: push the branch and confirm the first real
   run's gates (checkout → PHP setup → Composer validate → Composer install →
   `./scripts/lint.sh` → ShellCheck).
2. **`actionlint` ran without `pyflakes`/`shellcheck` integration locally**,
   because the local container has neither. Its GitHub Actions expression,
   input-name and shell-injection checks did run and did catch the real
   `tools-cache` defect; actionlint's own Python linting of `run:` blocks is
   therefore verified only to the extent ShellCheck covered those blocks (it
   flagged none).
3. **The host has no `composer` and no `shellcheck`**, so all gates ran in
   Docker. Composer's behaviour was reproduced with the real `composer:2`
   binary (2.10.3, the same version as Stage C) and ShellCheck with both the
   apt package CI installs (0.10.0) and upstream 0.11.0. The
   `shivammathur/setup-php@v2` PHP build itself was not exercised (that
   action downloads its own build).
4. **Pre-existing follow-ups (unchanged by this stage, not Stage D failures):**
   - PHPCS legacy debt remains (3290 errors + 2672 warnings); `composer
     lint` / `composer check` are red **by design**.
   - PHPStan legacy baseline remains (298 errors across 199 entries).
   - PHPStan 2.x upgrade decision remains open (1.12.x prints an "old
     version" notice on every run).
   - PHP `Requires PHP:` header alignment (runtime headers declare 7.4/8.0
     while the standard's floor is 8.0 and the runtime is 8.5) remains
     later-stage work — CI does not touch it.
   - CSS indentation standard amendment remains open.
   - Stage E's unified test harness and Stage F's theme split remain
     unimplemented; CI has no Docker/WordPress-boot job by design.
   - The `composer analyse` script uses `--memory-limit=2G` (deviating from
     the standard §1.4 template's 1G, per Stage C's measurement). Unchanged
     here; a standard amendment is still owed.
