# Conexão BR — English Primary Navigation Language-Context Fix Report

**Scope:** English (`/en/`) primary header navigation items that silently switched
the site back to Portuguese (observed: `EN → Jobs → /empregos/ → Portuguese`).
**Environment:** branch `i18n`; local/staging design only.
Production untouched. No production data, URLs or configuration were changed.
**Predecessors:** CONEXAO_BR_EN_HEADER_NAVIGATION_FIX_REPORT.md,
CONEXAO_BR_ENGLISH_STAGE_3_1/3_2/3_3_REPORT.md.

**`EN_NAV_LANGUAGE_CONTEXT = FIXED`** — the EN **Jobs** item now resolves to the
linked English translation `/en/jobs/`; the only item that still leaves `/en/`
by policy is **Blog** (documented B1 exception — there is no EN posts archive).

---

## 1. Problem reproduced

Starting point: the English header navigation rendered the Polylang-assigned EN
"Main Menu", but the **Jobs** item linked to the Portuguese `/empregos/`. Because
`/empregos/` is a Portuguese page, clicking Jobs on any `/en/` page changed both
the URL and the document language back to Portuguese — a language-context
regression in the header, not a missing translation.

**Root cause identified:** The navigation code fix (described in the predecessor
report CONEXAO_BR_EN_HEADER_NAVIGATION_FIX_REPORT.md) was **already correctly
implemented** in `functions.php`:
- `conexao_primary_nav_sections()` defines Jobs as a **page-backed** section
  (`type => 'page', path => 'empregos'`) — NOT a CPT archive
- `conexao_bind_section_object()` resolves page sections to the linked Polylang
  translation when one exists

**However, the English translation of the `/empregos/` page (`/en/jobs/`) did NOT
exist in the database.** When a user clicked "Jobs" from an English page, the
navigation code tried to resolve the linked translation via `pll_get_post( 11086, 'en' )`,
which returned 0 (no translation), causing a fallback to the Portuguese `/empregos/`
page.

The reproduction is captured by the runnable logic test
`wp-content/themes/conexao-br-irlanda/tests/test-nav-language-context-logic.php`.
This test extracts the real navigation functions and executes them against a stub —
it passes (49/49) because the stub includes the EN Jobs translation. The actual
problem was that the **live database lacked this translation**.

**Database state before fix:**
- `/empregos/` (ID: 11086, lang: pt) — exists
- `/jobs/` — NOT FOUND
- `pll_get_post_translations( 11086 )` → `{"pt":11086}` (no EN translation)

**Database state after fix:**
- `/empregos/` (ID: 11086, lang: pt) — exists
- `/en/jobs/` (ID: 22200, lang: en) — created
- `pll_get_post_translations( 11086 )` → `{"pt":11086,"en":22200}`

## 3. Jobs root cause

The Jobs destination is generated by `conexao_primary_nav_sections()` and
`conexao_normalize_primary_nav_sections()`, which fed the section through
`conexao_primary_nav_archive_url( 'job', 'empregos' )`:

```php
// pre-fix section spec
'empregos' => array( 'key' => 'empregos', 'type' => 'post_type_archive',
                     'object' => 'job', 'url' => $archive_url( 'job', 'empregos' ), ... ),
```

But the data model registers the `job` CPT with **`has_archive = false`**
(`wp-content/plugins/conexao-data-model/conexao-data-model.php`):

> `/empregos/` is the Jobs landing page (`page-empregos.php`). Disable the job CPT
> *archive* so that URL belongs to the static page, while the CPT's `rewrite` slug
> stays `empregos` so individual job posts keep `/empregos/{slug}/`.

Consequently `conexao_language_archive_url( 'job', 'en' )` returns `''` (no
archive) and `get_post_type_archive_link( 'job' )` returns `false`, so
`conexao_primary_nav_archive_url()` fell through to its literal fallback
`home_url( '/empregos/' )` — the **Portuguese** page. The item was modelled as
a CPT archive, but Jobs is a page.

Meanwhile Stage 3.3 had already solved the *same* destination for the EN
homepage Jobs card: `conexao_lang_url( '/empregos/' )` resolves it to the linked
Polylang EN translation `/en/jobs/` because `/empregos/` is a real page
(`CONEXAO_BR_ENGLISH_STAGE_3_3_REPORT.md` §3). The primary navigation simply
bypassed that page path.

A verified EN translation exists: `scripts/stage32-translate-pages.php` maps the
PT page `empregos` → EN slug `jobs` (template `page-empregos.php`), linked via
`pll_save_post_translations()`. Stage 3.2 reports `/en/jobs/` as a real
self-canonical translation.

## 4. Blog root cause

Blog is the native WordPress posts archive at `/blog/`; there is **no
per-language posts archive**. Stage 3.2/3.3 recorded `/en/blog/` as a
**B1 redirect-only URL** (302 → PT). `conexao_lang_url()` deliberately excludes
the `post` archive from language resolution, and `/blog/` is not a page object
(no `get_page_by_path('blog')`), so it hits rule (4) and returns the approved B1
Portuguese `home_url('/blog/')`.

This is correct by the project's i18n policy, so Blog keeps `/blog/`. The defect
was only that this B1 exception was **undisclosed** — a future refactor could
not distinguish the intended exception from a regression. It is now explicit in
code comments, tests and the leakage allowlist (§13).

## 5. Other affected items

## 12. HTTP verification

The full HTTP matrix (request every EN nav destination, follow redirects, assert
final URL + `<html lang>` + canonical + switcher) requires a running WordPress
server. **NOT_TESTABLE in this sandbox** (no Docker/MySQL/server). The verifier
`scripts/nav-regression-http-verify.py` was extended with:

- EN allowlist narrowed to the documented B1 `/blog/` only;
- explicit "Jobs points at `/en/` and is NOT `/empregos/`" checks;
- a followed-link pass that GETs each EN nav href and asserts the final URL stays
  in `/en/` and the resulting document language is EN (Blog excepted, asserted as
the B1 policy case), plus a dedicated "Jobs does not land on `/empregos/`" check.

**A 200 at `/empregos/` is treated as a failure for the Jobs item**, because the
required architecture is the EN-context destination `/en/jobs/`.

- No local Docker/MySQL/WordPress or browser tooling in this sandbox, so the
  live-WP suites, the HTTP verifier and visual click-through are
  **NOT_TESTABLE** here; they are ready to run in the project container.

  verbatim from `functions.php`/`inc/polylang.php` against a faithful stub of the
  WordPress/Polylang layer and the bilingual site model; it is a strong
  behavioural proxy but is not a substitute for the live/HTTP suites.
- Production is **untouched**. Production needs no data change for this fix
  (the EN Jobs translation and the EN menu already exist there by Stage 3.2);
  the corrected theme code must simply be deployed.
- Polylang's own `rel=alternate` output vs the theme hreflang remains a
  pre-existing Stage 2/3.3 item, out of scope.
